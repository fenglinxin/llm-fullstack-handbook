## 01 开篇导语

上一章我们画了一张全栈地图：一条大模型生产线 = 数据 → 预训练 → 微调/对齐 → 部署 → 推理优化 → 上线运维。

这一章不讲理论，只干一件事：**把它跑通。**

很多人的学习路径是这样的：先研究三个月预训练论文，再搭半天的多卡训练环境，结果连“微调后的模型到底长什么样”都没见过。我们反着来：**用一张 24GB 显卡（没有就用云 GPU），2 小时跑完“下载开源底座 → LoRA 微调 → 合并模型 → 起一个 OpenAI 兼容的推理服务”的最小闭环**，让一个领域 Demo 模型真正开口回答问题。

为什么必须先通？

因为链路没跑通之前，你根本不知道问题出在数据、训练还是部署；而链路一旦通了，后面每一章学到的数据清洗、预训练、对齐、量化、编译优化，都是在往这条已经能跑的链路上**替换更好的零件**——而不是从零拼一辆不知道能不能发动的车。

本章交付物：一个可复现的工程目录（含演示数据生成脚本、训练配置、合并配置、服务启动与验收脚本）。跑完，你就有自己的第一条 LLM 全栈生产线。

> 硬性前置：一张 NVIDIA 显卡（显存建议 16GB 以上，24GB 最佳；8GB 也能用文末降级路径），或一台按小时计费的云 GPU 主机。CPU 只能完成“下载＋推理”演示，2 小时内跑微调不现实。

## 02 最小闭环长什么样

先明确边界：本章**不做增量预训练、不做 RLHF、不做量化调优**，只打通“能改模型、能出服务”的最小链路：

~~~text
开源底座模型（Qwen2.5 系列，以官方仓库当日可下载版本为准）
   ↓ ① 数据：合成 120 条“公司帮助台”规则问答
   ↓ ② LoRA 微调：只训练一小撮低秩参数，让模型学会私有规则
LoRA adapter（几十 MB 的增量权重）
   ↓ ③ 合并导出：把 adapter 合并回底座，得到可直接部署的模型
领域微调模型
   ↓ ④ vLLM 服务：OpenAI 兼容接口 localhost:8000
业务代码调用：curl / OpenAI SDK
~~~

三个关键设计，先讲清楚为什么。

**① 为什么用 LoRA，不直接全参微调？**
全参微调要把 7B 模型的全部参数和优化器状态装进显存，24GB 单卡非常吃力。LoRA（Low-Rank Adaptation，低秩适配）只冻结原模型、额外训练一小撮低秩矩阵，通常只占全部参数的 1% 以内，显存和算力需求大幅下降，中小数据量下效果与全参微调差距很小。**它是单卡玩家和中小团队的事实标准起步方案。**

**② 为什么先“合成数据”？**
本章目的是通链路，不是做数据集。为了在 2 小时内让模型产生“肉眼可见”的变化，我们用一段脚本把 6 条私有规则扩写成 120 条问答——这本身就是工业界“规则→合成数据”的最小版本。真正的数据清洗与质量体系，第 04–10 章再展开。

**③ 为什么用 vLLM？**
vLLM 是目前开源生态里部署最普及的推理框架之一，提供 OpenAI 兼容接口，业务代码几乎零改动。先学会它，后面第 27 章做框架横向对比、第 28 章再深挖参数调优。

> 记住本章主线：**模型不是用来“训练完”的，是用来“上线被调用”的。** 所以每一步都以“能不能被 API 调到”为验收标准。

## 03 技术选型：三组关键选择

### 3.1 底座模型怎么选

| 档位 | 代表（示例） | 显存门槛（推理） | 适合谁 | 本章结论 |
|---|---|---|---|---|
| 7B 档 | Qwen2.5-7B-Instruct 类 | 24GB 左右更从容 | 想体验真实微调效果、显卡 24GB | 主推 |
| 3B 档 | Qwen2.5-3B-Instruct 类 | 12–16GB | 显卡 16GB 上下 | 备选 |
| 1.5B 档 | Qwen2.5-1.5B-Instruct 类 | 8GB（配合量化） | 显存小、只想通链路 | 降级路径 |

> 模型选择原则：**先选你能跑得动的最大模型，再谈效果**。模型名与版本以 Hugging Face / ModelScope 当日可下载的官方仓库为准，不要用记忆中的旧版本号写死。

### 3.2 微调框架怎么选

| 方案 | 优点 | 缺点 | 适合谁 |
|---|---|---|---|
| LlamaFactory（本章选） | 配置文件驱动、内置大量数据集格式与模板、CLI/WebUI 双入口、社区资料多 | 想深度魔改训练逻辑时不如直接写 Trainer | 第一次跑通、中小团队日常微调 |
| TRL（Hugging Face） | 与 transformers 生态一体，SFT/DPO/PPO 全家桶 | 需要自己写更多训练脚本与配置 | 想深入理解训练细节、后续做 RLHF |
| 自研训练脚本 | 完全可控 | 开发量大、易踩坑 | 有特殊需求的大团队 |

结论：**本章用 LlamaFactory 的 CLI**——它把“数据集注册、模板、LoRA、导出”这些最容易出错的地方封装好了，2 小时目标只能选它。

### 3.3 推理框架怎么选

| 方案 | 优点 | 缺点 | 适合谁 |
|---|---|---|---|
| vLLM（本章选） | 吞吐高、OpenAI 兼容、社区最普及 | 对 Windows 原生支持弱（建议 Linux/WSL2/容器） | Linux 服务端部署 |
| llama.cpp | 单文件、CPU/GPU 通吃、GGUF 量化 | 大并发吞吐一般 | 个人本机、边缘设备 |
| SGLang / TensorRT-LLM | 各有极致场景 | 上手门槛更高 | 第 27–30 章再展开 |

结论：**服务端演示用 vLLM**；如果你的机器是 Windows 且不想装 WSL，可以先用 llama.cpp 跑通“推理”这一步，微调仍建议在 Linux/云 GPU 上做。

## 04 分步实操：2 小时跑通（约 8 个 Step）

### Step 0 建工程目录（5 分钟）

在 Linux 服务器（或云 GPU 主机）上执行：

~~~bash
mkdir -p llm-demo/{data,configs,models,outputs,scripts}
cd llm-demo
~~~

最终目录结构（本章所有文件都按这个路径放）：

~~~text
llm-demo/
├── data/            # 数据集与 dataset_info.json
├── configs/         # 训练/合并 YAML 配置
├── models/          # 合并导出后的模型
├── outputs/         # LoRA adapter 输出
└── scripts/         # 数据合成与验收脚本
~~~

> 提示：Windows 用户建议用 WSL2 或云 GPU 主机；如果只想先看效果，也可以跳过训练，直接下载官方 Instruct 模型跑 vLLM。

### Step 1 装环境（15 分钟）

前置：NVIDIA 驱动已装好，能跑 nvidia-smi。然后创建 Python 环境并安装 PyTorch（CUDA 版）与 LlamaFactory：

~~~bash
# 1. 创建虚拟环境（Python 3.10/3.11 均可）
python3 -m venv .venv
source .venv/bin/activate

# 2. 安装 PyTorch（CUDA 12.x 示例；版本号以 pytorch.org 当日为准）
pip install torch --index-url https://download.pytorch.org/whl/cu124

# 3. 源码安装 LlamaFactory（官方仓库：github.com/hiyouga/LLaMA-Factory）
git clone https://github.com/hiyouga/LLaMA-Factory.git
cd LLaMA-Factory
pip install -e ".[torch,bitsandbytes]"
cd ..

# 4. 安装推理与客户端依赖
pip install vllm openai huggingface_hub modelscope
~~~

> 备选：不想折腾环境，直接用 PyTorch 官方 CUDA 镜像开容器（tag 以当日官方为准），训练与推理都在容器内完成，避免宿主机 CUDA 版本地狱。

### Step 2 下载底座模型（10–30 分钟，看网速）

二选一：海外网络用 Hugging Face，国内推荐 ModelScope。以下载 Qwen2.5-7B-Instruct 为例（显存小的换成 3B/1.5B 同名仓库即可）：

~~~bash
# 方式 A：Hugging Face（在 llm-demo 目录执行）
hf download Qwen/Qwen2.5-7B-Instruct --local-dir models/Qwen2.5-7B-Instruct

# 方式 B：ModelScope（国内更快）
modelscope download --model Qwen/Qwen2.5-7B-Instruct --local_dir models/Qwen2.5-7B-Instruct
~~~

下载完成后确认目录里有 config.json、tokenizer 相关文件与 safetensors 权重文件。

> 为什么先下到本地而不是让框架现下？一是训练与推理要复用同一份权重，二是断点续传与离线部署都依赖本地目录。这也是工业界的标准做法：**权重永远有本地副本和版本号**。

### Step 3 合成演示数据集（10 分钟）

本章 Demo 主题：**公司内部 IT 帮助台**。底座模型不知道你们公司的打印机型号、VPN 地址、工单流程，微调后它才会“按公司规则回答”——这正是私有化微调最常见的价值点。

先在 data 目录注册数据集（LlamaFactory 靠 dataset_info.json 找数据）：

~~~json
// data/dataset_info.json
{
  "demo_helpdesk": {
    "file_name": "demo_helpdesk.jsonl",
    "formatting": "alpaca",
    "columns": {
      "prompt": "instruction",
      "query": "input",
      "response": "output"
    }
  }
}
~~~

再保存下面的生成脚本为 scripts/make_demo_data.py，运行后生成 120 条问答：

### Step 4 LoRA 微调（20–40 分钟）

保存训练配置为 configs/demo_sft.yaml（24GB 显卡主推；显存小于 20GB 时加最后两行开 QLoRA）：

~~~yaml
# configs/demo_sft.yaml
model_name_or_path: models/Qwen2.5-7B-Instruct
template: qwen
stage: sft
finetuning_type: lora
dataset_dir: data
dataset: demo_helpdesk
cutoff_len: 1024
max_samples: 120

per_device_train_batch_size: 2
gradient_accumulation_steps: 4
learning_rate: 2.0e-4
num_train_epochs: 3.0
lr_scheduler_type: cosine
warmup_ratio: 0.1

bf16: true
lora_rank: 16
lora_alpha: 32
lora_dropout: 0.05

logging_steps: 5
save_steps: 20
output_dir: outputs/helpdesk-lora
plot_loss: true

# 显存 < 20GB 时追加（QLoRA 4bit）：
# quantization_bit: 4
# quantization_method: bitsandbytes
~~~

执行训练（在 llm-demo 目录、虚拟环境内）：

~~~bash
CUDA_VISIBLE_DEVICES=0 llamafactory-cli train configs/demo_sft.yaml
~~~

看到类似 “TrainOutput(global_step=…, training_loss=…)”、“Saved adapter model” 即成功。adapter 会输出到 outputs/helpdesk-lora。

> 训练中途可以另开终端用 nvidia-smi 观察显存：7B + LoRA（BF16）约占用 18–22GB；如果接近 24GB 上限，把 cutoff_len 降到 512 或 batch 改为 1 即可。

### Step 5 合并导出（5 分钟）

LoRA adapter 只是增量权重，直接部署要同时加载底座和 adapter，容易出版本问题。工业界标准做法：**训练完合并成一个完整模型**再交付。

保存合并配置为 configs/export.yaml：

~~~yaml
# configs/export.yaml
model_name_or_path: models/Qwen2.5-7B-Instruct
adapter_name_or_path: outputs/helpdesk-lora
template: qwen
finetuning_type: lora
export_dir: models/helpdesk-merged
export_size: 2
export_legacy_format: false
~~~

执行：

~~~bash
llamafactory-cli export configs/export.yaml
~~~

导出完成后检查 models/helpdesk-merged 目录包含 config.json、tokenizer 相关文件与 safetensors 权重，即合并成功。

### Step 6 起 vLLM 服务（5 分钟）

~~~bash
vllm serve models/helpdesk-merged \
  --served-model-name helpdesk \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.90 \
  --port 8000
~~~

看到 “Application startup complete” 后，另开终端验证：

~~~bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"helpdesk","messages":[{"role":"user","content":"打印机连不上怎么办？"}],"max_tokens":300}'
~~~

> 说明：curl 命令中的换行符是“反斜杠续行”，复制到 Windows PowerShell 时请改成一行，或直接用下面的 Python 脚本。

### Step 7 验收：微调前后对比（10 分钟）

保存 scripts/ask.py 并运行：

~~~python
# scripts/ask.py —— 调用本地 vLLM 服务并计时
import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

questions = [
    "打印机连不上怎么办？",
    "在家连不上公司 VPN 怎么办？",
    "公司 WiFi 连不上，怎么排查？",
]

for q in questions:
    start = time.time()
    resp = client.chat.completions.create(
        model="helpdesk",
        messages=[{"role": "user", "content": q}],
        temperature=0.2,
        max_tokens=300,
    )
    cost = time.time() - start
    print("问题：", q)
    print("回答：", resp.choices[0].message.content)
    print("耗时： %.2f 秒" % cost)
    print("-" * 40)
~~~

## 05 参数详解：本章用到的核心配置

| 参数 | 含义（大白话） | 本章取值 | 调优方向 |
|---|---|---|---|
| lora_rank | LoRA 低秩矩阵的“宽度”，越大容量越大 | 16 | 数据多/任务难可试 32–64；数据少用 8–16 防过拟合 |
| lora_alpha | LoRA 缩放系数，通常与 rank 按 2:1 搭配 | 32 | alpha 偏大=改动幅度大；一般保持 alpha=2×rank 起步 |
| lora_dropout | 训练时随机丢弃比例，防过拟合 | 0.05 | 数据少可加到 0.1 |
| learning_rate | 每步参数更新步长 | 2e-4 | LoRA 常见 1e-4~3e-4；全参 SFT 常用 1e-5~2e-5 |
| num_train_epochs | 全量数据过几遍 | 3 | 数据干净可 2–3；数据少或任务简单可 3–5（要盯验证 loss） |
| cutoff_len | 单样本最大 token 长度，超长截断 | 1024 | 长文档任务要加长，代价是显存与训练时间 |
| per_device_train_batch_size × gradient_accumulation_steps | 等效 batch = 两者相乘 | 2×4=8 | 等效 batch 8–32 是 SFT 常见区间 |
| warmup_ratio | 前多少比例步数线性升温 | 0.1 | 数据少可 0.03–0.1；防止起步震荡 |
| max_model_len（vLLM） | 服务支持的最大上下文长度 | 4096 | 长上下文需求再加，显存不够就降 |
| gpu-memory-utilization | vLLM 最多用多少比例显存 | 0.90 | 留一点给驱动与并发缓冲，别设 1.0 |

> 记住一条铁律：**参数没有“唯一最优”，只有“场景最优”**。任何参数改动都要配一次微调前后对比，否则就是玄学调参（第 18 章专门讲实验管理）。

## 06 高频踩坑排查（本章至少会遇到 3 个）

**坑 1：训练时 CUDA Out of Memory**
症状：刚起步就报 torch.OutOfMemoryError。
原因：7B 模型 + 优化器 + 激活值超过显存。
解法（按顺序试）：把 cutoff_len 降到 512 → batch 改 1 → 开 QLoRA 4bit（configs 里追加 quantization_bit: 4）→ 换 3B 模型。**不要一上来就买显卡，先降配置跑通。**

**坑 2：训练正常，但回答是乱码/复读机**
症状：loss 在降，生成内容却像“啊啊啊…”。
原因：chat template 与模型不匹配，或 temperature 太高、max_tokens 太小。
解法：确认 configs 里 template 与底座一致（Qwen 用 qwen，Llama 用 llama）；推理时 temperature 设 0.2 左右，max_tokens 给足；先 curl 直接问官方模型排除服务问题。

**坑 3：loss 几乎不降，或训完还是答非所问**
症状：训练 loss 从 0.0x 开始或一直震荡。
原因：数据集没被正确读取（dataset_info 拼写错、路径错），或 instruction/input/output 字段没对上。
解法：训练日志里看 “Dataset: demo_helpdesk” 与样本数是否为 120；打印一条预处理后的样本检查模板拼接；确认 data/dataset_info.json 的 columns 映射正确。

**坑 4：合并导出后模型加载报错/尺寸不匹配**
症状：export 报 adapter 与 base 的 shape 不一致，或服务启动时 config 报错。
原因：底座路径与训练时不一致、adapter 目录选错、合并时 template 写错。
解法：export 配置的 model_name_or_path 必须与训练配置完全同目录；adapter_name_or_path 指到 outputs/helpdesk-lora（含 adapter_config.json 的目录）；合并后先本地 transformers 加载一次再上服务。

**坑 5：客户端报 404 model not found**
症状：curl/OpenAI SDK 能连上 8000 端口，但报 model 不存在。
原因：请求里的 model 名与 vllm serve 的 --served-model-name 不一致。
解法：统一用 helpdesk；或用 curl http://localhost:8000/v1/models 查看服务端实际模型名。

**坑 6：pip 装 torch/vllm 装了半天还失败**
症状：版本冲突、找不到 cu124 索引、vllm 编译报错。
原因：Python 版本过新/过旧，或没先装好 CUDA 版 torch。
解法：用 Python 3.10–3.11 + 官方 cu124 索引装 torch 后再装 vllm；最稳的是直接用 LlamaFactory/vLLM 官方 Docker 镜像，宿主只负责装 NVIDIA 驱动。

> 如果 2 小时被环境问题吃掉 1.5 小时，正确姿势是：**换官方镜像或云 GPU 模板机**，把时间花在链路上而不是编译上。

## 07 进阶优化：跑通之后还能做什么

**① QLoRA 降显存**：把量化与 LoRA 结合，7B 模型在 8–12GB 显卡上也能微调（效果会比 BF16 LoRA 略降，需对比验证），这是第 31 章量化的提前预习。

**② 建立“微调前后基线”**：把 Step 7 的 3 个问题扩成 20–50 条领域评测题，微调前后各跑一遍并记录回答，这是第 20 章评估体系的最小雏形。**没有基线的微调，等于蒙眼开车。**

**③ 用 Git 管好“模型版本”**：把 models/Qwen2.5-7B-Instruct（底座）、outputs/helpdesk-lora（adapter）、models/helpdesk-merged（合并产物）分别登记版本与训练配置 hash，后续第 44 章模型迭代就靠这套习惯。

**④ 走向对齐**：把 Step 4 的 stage 从 sft 换成 dpo（需要偏好数据），就能体验 DPO 对齐；第 23–25 章会把奖励模型、RLHF/PPO、RLAIF 讲透。

**⑤ 换“真领域”**：把帮助台规则换成你的业务知识（产品手册、客服话术、内部 SOP），数据量从 120 扩到几千条，就是企业 PoC 的真实起点——第 42 章会讲完整立项流程。

## 08 本章核心总结（TOP3）

**TOP1**：最小闭环 = “下载底座 → LoRA 微调 → 合并导出 → vLLM 服务 → API 验收”五步；先通链路再谈优化，任何一步跑不通都先降级（小模型/QLoRA/短上下文），不要卡在环境上。

**TOP2**：LoRA 是单卡微调的事实标准起步方案——冻结原模型只训 1% 以内的低秩参数；数据、模板、路径是三个最容易出错也最值得先检查的点。

**TOP3**：微调的价值要用“前后对比”证明：同一条私有规则问题，底座会一本正经地编造，微调后按公司规则回答。**从第一天就建立评测基线与模型版本习惯**，后面所有章节的优化才有落点。
