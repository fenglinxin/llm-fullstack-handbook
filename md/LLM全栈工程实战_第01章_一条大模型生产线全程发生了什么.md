## 01 开篇导语

先问一个问题：**你印象里的“大模型开发”，是写几行代码调 API，还是下载开源模型跑一次微调？**

如果你只做过这两件事，那这篇文章就是为你准备的——因为这两件事，离“工业级 LLM 工程”还差得很远。

真正把一个大模型放进生产环境，是一条完整的流水线：**先要有海量干净数据，把底座模型训练出来；再通过微调和对齐，让它懂你的业务、守你的规矩；然后把它压进显卡、调成服务，扛住真实流量；最后还要在推理引擎和编译器层面一层层抠性能**。数据、训练、对齐、部署、优化、运维，任何一环出问题，前面的努力都会归零。

更扎心的是：这条流水线的每一环，网上都有人讲，但讲数据的人不碰训练，讲训练的人不碰部署，讲部署的人不讲编译器——**知识全是碎片，连不成一条能落地的线**。

本篇不写代码、不堆公式，只干一件事：**给你一张 LLM 全栈工程地图，并告诉你这个 46 章专栏会怎么带你沿着它走完**。看完，你能回答三个问题：一条大模型生产线到底有哪些环节？每个环节解决什么问题？我该按什么顺序学？

## 02 一条大模型生产线，比你想象的长得多

把“工业级 LLM 工程”拆开，其实是五段固定的流水线（主线工程口径，后续 46 章都按这条线走）：

**① 数据层：决定模型上限**
预训练、微调、对齐，全部吃数据。原始语料要先采集、清洗、过滤、去重、脱敏、打分，再按配比组装成训练集。业界有句话：“垃圾进，垃圾出”——**数据质量直接决定模型上限，模型结构只是在逼近这个上限**。这一层对应本专栏第 03–13 章。

**② 训练层：把数据炼成模型**
用清洗好的数据训练底座模型（预训练），或在开源底座上继续训练（增量预训练）。之后再进入微调与对齐：SFT 让模型学会“按指令回答”，DPO/RLHF 让回答更符合人类偏好。这一层对应第 14–26 章。

**③ 部署层：让模型跑起来**
训练出来的权重只是一堆数字，要把它加载进推理框架、配上 KV Cache 和批处理策略，变成 OpenAI 兼容的服务接口，才能被业务调用。显存不够就量化，并发不够就调调度。这一层对应第 27–34 章。

**④ 编译器/内核层：把每一毫秒榨出来**
当服务上线后发现时延高、吞吐低，就要往底层走：算子融合、计算图编译、动态 shape 适配、投机推理、并行调度、手写内核。**这一层是资深工程师和普通调包侠的分水岭**，对应第 35–40 章。

**⑤ 落地与运维层：让模型持续可靠**
全链路串联、领域定制、高并发适配、端侧部署、模型迭代评测、线上故障排查，最后沉淀成团队可复用的工程化流程。对应第 41–46 章。

> **记住这张图：数据 → 预训练 → 微调/对齐 → 部署 → 推理优化 → 上线运维。** 后续每一章，都只是把其中一小段放大、讲透、做成能跑的工程。

**为什么“会调 API”不算入门？**
调 API 只用到流水线的最末端：别人把数据、训练、部署全做完了，你只负责传参。一旦遇到业务要私有化、要定制领域能力、要控制成本、要低时延，API 背后的每一层问题都会变成你的问题。本专栏的定位，就是帮你把这些问题逐层拆掉。

## 03 全栈工程的核心概念：先认识“记分牌”和“工具箱”

这一章不要求你立刻弄懂所有概念，但有两个东西必须现在建立印象：**全栈的“记分牌”（指标）**和**全栈的“工具箱”（工具生态）**。后面每一章都是在跟这些数较劲、往这套工具箱里填零件。

### 3.1 训练侧的记分牌

| 指标 | 大白话 | 什么时候看 |
|---|---|---|
| Loss（训练损失） | 模型预测下一个 token 的错误程度，越低说明拟合越好 | 全程看，判断是否收敛 |
| 验证集 Loss | 在没见过的数据上的损失，防止“背题” | 判断过拟合/欠拟合 |
| 梯度范数 | 梯度的大小，异常大或异常小都危险 | 判断训练是否稳定 |
| MFU | 显卡理论算力被用上了百分之几 | 判断训练效率（是否在烧钱空转） |
| 训练吞吐 | 每秒/每天处理多少 token | 估算工期与成本 |
| 收敛速度 | loss 降到目标值需要多少数据/步数 | 判断数据与超参是否合理 |

> 训练世界里，**MFU 低＝显卡在摸鱼**；loss 不降、梯度爆炸、吞吐上不去，是三大高频事故，第 13 章专门讲。

### 3.2 推理侧的记分牌

| 指标 | 大白话 | 什么时候看 |
|---|---|---|
| TTFT（首 token 时延） | 用户发出请求后，等多久看到第一个字 | 聊天体验、流式场景 |
| TPOT（每输出 token 耗时） | 生成下一个字平均要多久 | 决定“打字速度” |
| ITL（token 间延迟） | 相邻两个输出字的时间间隔（与 TPOT 常混用，口径以实测为准） | 流式输出流畅度 |
| 吞吐（tokens/s、req/s） | 单位时间能服务多少请求/生成多少字 | 成本与容量规划 |
| 并发与排队时延 | 同时服务多少请求、高峰排队多久 | 高并发场景 |
| 显存占用 | 权重＋KV Cache＋临时缓冲占多少显存 | 决定能部署多大模型、多长上下文 |

> 推理优化里最常见的取舍，是**时延、吞吐、显存三者互相拉扯**：想快就要多占显存和算力，想省就要牺牲一点速度。第 27–40 章的大量优化，本质都是在找这三者的平衡点。

### 3.3 全栈工具箱（先认识，不展开）

| 环节 | 代表工具/框架（举例） | 一句话定位 |
|---|---|---|
| 数据管道 | 自研 pipeline＋开源清洗库（如 Data-Juicer 一类） | 清洗、去重、过滤、打分的流水线 |
| 预训练 | Megatron-LM、DeepSpeed、FSDP 等 | 大规模分布式训练 |
| 微调/对齐 | TRL、LlamaFactory、OpenRLHF、verl 等 | 把训练流程封装成可配置操作 |
| 推理服务 | vLLM、SGLang、TensorRT-LLM、llama.cpp 等 | 把权重变成高性能服务 |
| 评测与运维 | 评测集/框架＋监控告警体系 | 回答“改好了没有、上线稳不稳” |

> 注意：**工具名单会随时间更新，本专栏每章写到的工具都以发文当月的官方仓库为准**，不背过期版本号——这是本专栏防幻觉的硬规矩。

## 04 全景选型地图：每一层都有三条路

整个 LLM 全栈工程，选型永远在回答同一个问题：**这层用云、用开源、还是自研？** 先给你一张概览地图（细节由后续对应章节展开，现在看框架即可）：

| 流水线环节 | 干什么 | 云 API 路线 | 开源组件路线 | 自研路线 | 新手首推 |
|---|---|---|---|---|---|
| 数据 | 清洗/去重/打分 | 商用清洗标注平台 | Data-Juicer 等开源工具 | 自研分布式管道 | 先用开源工具＋脚本，跑通再升级 |
| 预训练 | 从零训练底座 | 极少有（算力与数据门槛极高） | 开源框架＋开源语料 | 大厂才需要 | 先不碰全量预训练，从增量预训练学起 |
| 微调/对齐 | 让模型懂业务 | 云厂商微调服务 | TRL/LlamaFactory 等 | 自研训练平台 | 开源框架本地跑通，再考虑托管 |
| 推理 | 模型变服务 | 模型 API | vLLM/SGLang 等 | 自研推理引擎 | vLLM 单卡跑通 |
| 优化 | 压时延/提吞吐 | 云厂商自动优化 | 量化/编译工具链 | 自研 kernel | 先量化，再学编译优化 |
| 运维 | 上线与迭代 | 云托管运维 | K8s＋监控开源栈 | 自研平台 | 先做好指标采集与日志 |

三条选型原则，全系列通用：

1. **先通后优**：第一条能跑通的链路，永远比完美的架构重要；
2. **先云后自建**：验证阶段用云换时间；规模与定制需求明确后再自建；
3. **先开源后魔改**：开源项目的文档、社区、示例齐全，是学习性价比最高的起点。

> 特别提醒：**“从零预训练”是门槛最高的路线**，个人开发者不建议一上来就做。本专栏第 03–13 章讲预训练与数据，是为了让你理解原理、能在企业环境落地，同时给出“增量预训练／微调”这条单卡也能跟跑的替代主线——顺序不要搞反。

## 05 主线工程：把 46 章串成一条真项目

本专栏 = 一个贯穿始终的**主线工程** + 一份**逐层放大的章节地图**。

主线工程是一套“**领域大模型生产流水线**”：以开源底座模型为载体，从领域数据管道开始，依次走过增量预训练（CPT）→ SFT → 对齐（DPO/RLHF 视算力可选）→ 部署 → 推理优化 → 上线评测的完整生命周期。

- 目标场景：**企业私有化领域问答助手**（知识密集、格式要求高、数据不出域）；
- 规模口径：**1B–14B 模型、1–8 卡**——普通团队和个人可复现；每章同时给出企业大规模版的扩展要点；
- 单卡降级路径：显存不够时，用 QLoRA、量化、小模型、子集数据等替代方案跟跑，保证零基础不掉队。

**学习路径建议**（三种身份三条路线）：

| 身份 | 推荐路径 | 说明 |
|---|---|---|
| 算法/数据新人 | 01 → 02 → 数据季（03–13） → 训练对齐季（14–26） | 先把“数据决定上限”刻进肌肉记忆 |
| 后端/推理工程师 | 01 → 02 → 部署季（27–34） → 编译季（35–40） → 回头补数据季 | 从能跑服务开始，再往两端补 |
| 团队负责人/架构师 | 01 → 02 → 落地季（41–46） 打底，再按团队短板补对应阶段 | 先有全局观与流程，再补细节 |

## 06 本章实操：三张表，把“学会”变成动作

本章的“实操”不敲代码，而是建立三个贯穿全系列的学习动作——**每学一章，更新你的三张表**。这也是后续所有章节的“知识收纳盒”。

**第一张表：生产线拆解表**
把你正在做（或想做）的 LLM 产品写下来，按“数据 → 预训练/增量预训练 → 微调 → 对齐 → 部署 → 优化 → 运维”拆开，每一段标注：现在有没有方案？是云、开源还是自研？如果某一段写不出来——恭喜，这就是你下一章要学的内容。

**第二张表：候选方案清单**
针对每一段，收集 2–3 个候选方案，只记四列：方案名、要钱还是要机器、上手难度、官方文档地址。不急着选，先把“货架”看清楚。本专栏每一章的选型对比，都可以直接抄进这张表。

**第三张表：指标基线表**
给每一段写下你预期的核心指标（如训练 loss 目标、推理 TTFT 目标、单卡并发数），后续章节教了实测方法后，再回来把“预期”改成“实测”。**这张表就是你未来做优化的起点**——没有基线，就没有优化。

> 建议现在就打开备忘录建这三张表。第 02 章我们就要用它们跑通第一个最小闭环。

## 07 新手最容易掉的五个坑（本专栏每一章都会带避坑）

**坑 1：把“调 API”当成“做大模型”**
症状：会写 prompt、会接 SDK，遇到私有化/定制/成本问题就束手无策。解法：先建立全栈地图（本篇），再按主线工程逐层补课——你缺的不是某个技巧，是数据、训练、部署的系统能力。

**坑 2：按名词零散学，不按流水线学**
症状：今天刷一篇 LoRA，明天看一个 vLLM 教程，后天又去研究量化，每个都“好像懂了”，连起来全不会。解法：以主线工程为骨架，一次只在一个环节里深挖，学完立刻装回主线——这就是本专栏的章节顺序。

**坑 3：忽略数据，一上来就调模型**
症状：微调效果差，反复调学习率、调 rank，最后发现是数据集里重复样本占一半、答案本身是错的。解法：把“数据体检”放在调参之前：去重、清洗、质检、配比，先保证数据没有硬伤（第 04–10 章）。

**坑 4：一上来就想从零预训练**
症状：个人开发者想复刻 GPT，先卡在算力和数据上几个月，项目夭折。解法：先跑通“开源底座＋增量预训练＋微调”的轻量主线；理解预训练原理后，再在有企业资源时做全量预训练（第 03、11 章讲清两者边界）。

**坑 5：选模型只看榜单，不看部署代价**
症状：选了个“最强”大模型，结果单卡放不下、时延超预算、并发上不去。解法：任何选型先问三个问题：显存够吗？TTFT/TPOT 达标吗？单位 token 成本多少？评测榜单只是起点，工程指标才是终点（第 20/27/31 章展开）。

> 进阶提醒：以上五个坑的共同根源是**没有“分层认知”**。把模型、数据、算力、服务看成互相约束的四层，任何决策都问一句“改这一层，其他三层会怎样”，你就已经超过大多数调包选手了。

## 08 本章核心总结（TOP3）

**TOP1**：工业级 LLM 工程是“数据 → 预训练 → 微调/对齐 → 部署 → 推理优化 → 上线运维”的完整流水线，任何一环都会决定项目成败；调 API 只摸到了流水线末端。

**TOP2**：全栈有两套记分牌——训练侧看 loss、梯度范数、MFU、吞吐；推理侧看 TTFT、TPOT、并发与显存。**所有后续优化都是在跟这些数较劲**，先建指标基线，再谈优化。

**TOP3**：学习与选型都遵循“先通后优、先云后自建、先开源后魔改”，用“生产线拆解表＋候选方案清单＋指标基线表”三张表收纳每一章的知识，并把所有章节串进“领域大模型生产流水线”这一条主线工程。
