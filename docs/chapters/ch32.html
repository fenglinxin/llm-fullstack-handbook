01 开篇导语

模型压缩有三板斧：量化（改数值精度，已讲）、蒸馏（换小架构，第 22 章）、剪枝（删冗余参数/结构，本章）。三者可以单独用，也可以组合——但组合顺序和取舍完全不同。

剪枝的思路很直接：大模型里大量权重接近零、很多注意力头/神经元是冗余的，删掉它们应该不影响效果？

现实要打两个折扣：

  1. LLM 的权重分布有 outlier，朴素“删小权重”会严重伤模型——需要 SparseGPT/Wanda 这类考虑激活/误差补偿的方法；
  2. 稀疏不一定更快：非结构化稀疏需要专用 kernel 才有加速，通用框架里可能反而更慢。

所以本章的重点不是“怎么删”，而是“该不该剪、剪哪种、怎么恢复、和量化/蒸馏怎么排”。

一句话记住本章：剪枝的收益 = 稀疏率 × 硬件支持 × 恢复训练质量；对 LLM 而言，“结构化/半结构化 + 恢复训练”才是工程现实。

02 白话原理：三种剪枝粒度

类型 删什么 加速条件 效果风险
非结构化 任意单个权重 需要稀疏 kernel 精度损失大、难加速
半结构化 2:4 每 4 个删 2 个（固定模式） NVIDIA 稀疏内核 精度较可控
结构化 整行/整列/头/层 常规 kernel 即可 容量损失大
  • 重要性度量：不是“谁小删谁”，而是“删了谁对输出影响小”——常见度量：权重幅度、激活幅度（Wanda）、二阶误差补偿（SparseGPT）；
  • 恢复训练：剪完必须用少量数据微调（recovery fine-tuning），把损伤补回来；
  • 层/头剪枝：删掉冗余注意力头或整层（结构最简单，但要先做“冗余度分析”）。

记忆锚点：非结构化剪枝是“把布料剪成镂空”，半结构化是“按花纹剪”，结构化是“直接裁掉一块”——裁法越规整，硬件越好加速，但下手越重。

03 压缩决策框架：先选路线再动手

目标 首选路线 说明
省显存（权重变小） 量化 INT4/FP8 最成熟，先做
换小模型（端侧） 蒸馏 7B→3B，效果可控
同架构提速 量化+kernel 优化 剪枝提速依赖稀疏内核
极限压缩 蒸馏+量化，再评估剪枝 剪枝放最后、收益不确定
结构瘦身 头/层剪枝 需要冗余分析与恢复训练

组合顺序建议：先蒸馏（架构变小）→ 再量化（数值变小）→ 最后考虑剪枝；剪枝放在量化前做会更伤，通常“剪+恢复”后再量化。

生产现实：LLM 场景中，量化与蒸馏的 ROI 远高于通用剪枝；剪枝多用于科研/特定硬件（稀疏加速器）或作为压缩组合的最后一步。

04 剪枝方法选型

方法 类型 思路 落地难度
幅度剪枝 非结构化 删绝对值小的权重 低（但 LLM 效果差）
Wanda 非结构化 权重×激活幅度 中
SparseGPT 非结构化 逐层最小化重建误差 中高
2:4 半结构化 固定模式 配合稀疏 kernel 中（需硬件支持）
头/层剪枝 结构化 冗余分析后删组件 中（需恢复训练）

无论哪种：剪完必须做恢复训练（recovery fine-tuning），并跑与第 31 章相同的质量回归三板斧。

05 分步实操：压缩路线规划与稀疏度探测（约 40 分钟）

Step 1 压缩路线助手（5 分钟）

保存 scripts/compress_plan.py：

# scripts/compress_plan.py —— 压缩路线建议
# 用法：python compress_plan.py <memory|speed|edge|extreme> <distilled:y/n> <quantized:y/n>
import sys

target = sys.argv[1] if len(sys.argv) > 1 else "memory"
distilled = (sys.argv[2] if len(sys.argv) > 2 else "n").lower() == "y"
quantized = (sys.argv[3] if len(sys.argv) > 3 else "n").lower() == "y"

if target == "memory" and not quantized:
    print("路线：量化 INT4/FP8（先做）")
elif target == "edge" and not distilled:
    print("路线：蒸馏 7B->3B -> 量化；剪枝评估放最后")
elif target == "speed":
    print("路线：量化 + kernel 优化（剪枝需确认硬件稀疏内核）")
elif target == "extreme":
    print("路线：蒸馏 -> 量化 ->（可选）2:4 剪枝；每步做质量回归")
else:
    print("当前状态已满足目标，或先完成蒸馏/量化再评估剪枝")

试几个场景：

python scripts/compress_plan.py memory n n
python scripts/compress_plan.py edge n n
python scripts/compress_plan.py extreme y y

Step 2 稀疏度探测脚本（10 分钟）

保存 scripts/sparsity_probe.py：

# scripts/sparsity_probe.py —— 权重幅度分布与理论稀疏率探测
# 用法：python sparsity_probe.py <模型目录>
import json
import pathlib
import sys

import torch
from transformers import AutoModelForCausalLM

model_path = sys.argv[1] if len(sys.argv) > 1 else "models/helpdesk-sft-merged"
root = pathlib.Path(__file__).resolve().parent.parent

model = AutoModelForCausalLM.from_pretrained(model_path, torch_dtype=torch.bfloat16)
all_weights = []
layer_stats = []
for name, module in model.named_modules():
    if isinstance(module, torch.nn.Linear):
        w = module.weight.data.detach().float().abs()
        all_weights.append(w.flatten())
        layer_stats.append({"name": name, "params": w.numel(), "mean_abs": round(w.mean().item(), 6)})

all_weights = torch.cat(all_weights)
total = all_weights.numel()
report = {"model": model_path, "total_params": total, "thresholds": {}}
for q in (0.05, 0.1, 0.3, 0.5):
    t = torch.quantile(all_weights, q).item()
    frac = (all_weights <= t).float().mean().item()
    report["thresholds"][str(q)] = {"abs_threshold": round(t, 6), "frac_below": round(frac, 4)}

report["note"] = "幅度低不代表可安全删除：LLM 剪枝需激活感知/误差补偿+恢复训练"
out = root / "logs" / "sparsity_report.json"
with open(out, "w", encoding="utf-8") as f:
    json.dump(report, f, ensure_ascii=False, indent=2)
print(json.dumps(report, ensure_ascii=False, indent=2))

运行：

python scripts/sparsity_probe.py models/helpdesk-sft-merged
cat logs/sparsity_report.json

怎么看：frac_below 反映“按幅度阈值可删比例”的上限参考，但不是可安全删除比例——真正决策要靠 Wanda/SparseGPT 类方法在验证集上的表现。

Step 3 剪枝+恢复训练路线（如决定尝试，30–60 分钟）

  1. 用开源实现（如 SparseGPT/Wanda 的官方仓库，以仓库文档为准）对模型做 10%–30% 稀疏化，导出稀疏权重；
  2. 恢复训练必做：用第 26 章 cold_train 数据做 1–2 epoch LoRA/全参恢复微调（LR 取正常 SFT 的 1/3–1/2）；
  3. 导出合并后跑质量回归（eval_suite + 敏感任务 + 生成噪声检查）。

如果仓库/框架不支持你的模型架构，或恢复后掉点超红线，直接放弃剪枝路线——回到蒸馏+量化，不要硬撑。

路线 参数量 显存 吞吐 质量分 工程成本

06 参数详解：剪枝速查

参数 参考 说明

07 高频踩坑排查

坑 1：幅度剪枝直接用 症状：按绝对值删 30% 权重，模型变胡话。 解法：用 Wanda/SparseGPT 类激活感知或误差补偿方法；幅度只做参考。

坑 2：剪完不恢复训练 症状：稀疏权重直接上线，质量崩。 解法：恢复微调是剪枝的组成部分，不是可选项。

坑 3：剪了但没变快 症状：参数量少了，时延没降（kernel 不支持稀疏）。 解法：先确认硬件/框架支持（2:4 稀疏、专用内核）；不支持就只当“省显存实验”。

坑 4：拿参数量当效果 症状：参数量减半就宣布成功，任务分没测。 解法：质量回归三板斧照跑（同第 31 章）。

坑 5：粒度选错 症状：要部署加速却做非结构化剪枝。 解法：目标加速→半结构化/结构化+支持的 kernel；目标省显存→量化更省事。

坑 6：先剪后量化顺序错 症状：剪完再量化误差叠加，双重损伤。 解法：恢复训练后再量化；或直接蒸馏+量化组合跳过剪枝。

坑 7：忽略蒸馏这条更优路 症状：剪枝折腾两周，收益不如直接换 3B 蒸馏。 解法：先跑第 22 章蒸馏对比，剪枝只在必要时做。

08 进阶优化：剪枝的进化方向

① 2:4 半结构化：NVIDIA 稀疏内核支持固定 2:4 模式，配合恢复训练，是“真能提速”的主流剪枝形态。

② 结构化层/头剪枝：对冗余层/注意力头做“删除+恢复”，直接减少计算图规模，通用 kernel 即可收益。

③ Wanda/SparseGPT 工程化：官方仓库流程（校准集→剪枝→导出），与本章探测脚本衔接成 pipeline。

④ 联合压缩：蒸馏→剪枝（结构）→量化（数值）按序叠加，每步回归；只在极限压缩需求时采用。

⑤ 稀疏感知训练：训练时就加入稀疏正则/掩码（类似 QAT），让模型天生适应剪枝——成本高、收益稳。

09 本章核心总结（TOP3）

TOP1：压缩路线按 ROI 排序：量化 > 蒸馏 > 剪枝；剪枝分非结构化/2:4 半结构化/结构化，只有硬件支持稀疏内核才谈得上提速。

TOP2：LLM 剪枝必须“激活感知/误差补偿 + 恢复训练”：幅度剪枝不可直接用于 LLM；剪完跑质量回归三板斧。

TOP3：决策看“质量+显存+吞吐+工程成本”四列对比表，别拿参数量当效果；多数生产场景先走蒸馏+量化组合。
