01 开篇导语

第 41 章把生产线串了起来。但生产线本身要回答一个业务问题：“我们要做一个什么领域模型、花多少钱、达到什么效果？”

很多项目失败不是因为技术，而是因为立项阶段三件事没做：

  1. 需求没拆清（“做一个客服大模型”太模糊）；
  2. 路线拍脑袋（明明知识天天变，却选择微调而不是 RAG）；
  3. 没有成功指标（上线了也不知道算不算成功）。

本章给一套可复用的立项流程：需求拆解 → 数据摸底 → 路线决策 → PoC 设计 → 里程碑 → 验收上线，并提供一个能生成“项目计划书”的脚本。

一句话记住本章：领域项目 = 先回答“知识变不变、格式要不要、数据有多少、预算多少”，再决定路线；PoC 用 2–4 周和最小数据验证最关键的假设。

02 白话原理：需求拆解成“可决策的问题”

2.1 需求四问

问题 影响路线
知识会频繁更新吗？ 会→RAG 优先；稳定→可微调/CPT
需要固定格式/行为吗？ 要→SFT；只要检索→RAG
有多少领域文本/标注？ 多→CPT+SFT；少→RAG+少样本
算力/预算多少？ 决定全参/CPT/LoRA/云 API

2.2 需求拆解成能力清单

把“做一个 XX 助手”拆成能力项，例如 IT 帮助台：

  • 知识问答（覆盖知识库）
  • 分步/JSON/拒答等格式能力
  • 多轮上下文
  • 安全合规边界

每个能力项对应数据与评测要求——这就是第 20 章评测集的“需求源头”。

记忆锚点：立项的第一步不是选模型，是写“能力清单+验收标准”；写不出来就不该开工。

03 路线决策树与预算

3.1 路线决策表

画像 推荐路线 原因
知识高频更新 RAG 改知识不改模型
知识稳定+格式要求 LoRA SFT 便宜够用
大量领域文档+小标注 CPT/DAPT → SFT 先补知识底色
能力全面+预算充足 全参 SFT/RLHF 上限最高
只有 100 条数据 提示/RAG+少样本 别急着训
高合规风险 人工兜底+全链路审计 路线其次

3.2 预算三件套

  1. 数据成本：标注/清洗人天 × 单价（合成数据要加校验成本）；
  2. 算力成本：卡时估算（第 12 章方法）× 单价；
  3. 运维成本：GPU 池/推理/监控月费。

预算要写进立项书，并留 20%–30% 风险金（数据返工、评测不达标重训）。

3.3 PoC 设计（2–4 周）

周 目标
第 1 周 需求确认+数据摸底+基线（提示/RAG 方案）
第 2 周 种子数据 100–500 条+LoRA SFT+评测集 v1
第 3 周 路线 A/B 对比（RAG vs 微调 vs 组合）+调优
第 4 周 写 PoC 报告：效果、成本、风险、Go/No-Go 建议

PoC 的成功指标示例：领域题通过率≥80%、通用不掉、TTFT<1s、单次成本<X 元——上线前先写清楚“怎样算成功”。

05 分步实操：生成项目计划书（30 分钟）

Step 1 项目计划生成器（15 分钟）

保存 scripts/domain_project_plan.py：

# scripts/domain_project_plan.py —— 领域项目路线与计划生成器
# 用法：python domain_project_plan.py <项目名> <know_change:y/n> <need_format:y/n> <领域文档GB> <标注K条> [--gpu-hours 100] [--high-risk]
import pathlib
import sys

root = pathlib.Path(__file__).resolve().parent.parent
name = sys.argv[1]
know_change = (sys.argv[2] if len(sys.argv) > 2 else "n").lower() == "y"
need_format = (sys.argv[3] if len(sys.argv) > 3 else "y").lower() == "y"
doc_gb = float(sys.argv[4]) if len(sys.argv) > 4 else 0.0
labeled_k = float(sys.argv[5]) if len(sys.argv) > 5 else 1.0
gpu_hours = 100
high_risk = False
if "--gpu-hours" in sys.argv:
    gpu_hours = int(sys.argv[sys.argv.index("--gpu-hours") + 1])
if "--high-risk" in sys.argv:
    high_risk = True

if know_change:
    route = "RAG 优先（知识会变），微调只做格式/行为增强"
elif labeled_k < 1 and doc_gb < 5:
    route = "提示/RAG + 少样本（数据不足先别训）"
elif doc_gb >= 5:
    route = "DAPT/CPT（领域文档打底）→ LoRA SFT（格式行为）"
else:
    route = "LoRA SFT（种子 1k+ 起）+ 可选 RAG 补最新知识"

lines = ["# %s 项目计划书" % name, "",
         "## 1. 项目画像", "- 知识更新频率高: %s" % know_change,
         "- 需要固定格式/行为: %s" % need_format,
         "- 领域文档量: %.1f GB" % doc_gb, "- 标注数据: %.1f K 条" % labeled_k,
         "- GPU 预算: %d 卡时" % gpu_hours, "",
         "## 2. 推荐路线", "- " + route, "",
         "## 3. PoC 里程碑（4 周）",
         "- 第 1 周：需求确认 + 数据摸底 + 提示/RAG 基线",
         "- 第 2 周：种子数据与评测集 v1（100–500 条）",
         "- 第 3 周：路线 A/B 对比与调优",
         "- 第 4 周：PoC 报告（效果/成本/风险/Go-No-Go）", "",
         "## 4. 成功指标（示例）",
         "- 领域 held-out 通过率 ≥ 80%",
         "- 通用能力不掉出容忍线",
         "- TTFT < 1s（按业务调整）",
         "- 单次成本 < 预算线", ""]
if high_risk:
    lines += ["## 5. 高风险合规要求", "- 数据脱敏与来源审计（第 08 章）",
              "- 答案人工抽检 100%（关键场景）", "- 全链路日志与回滚预案", ""]

out = root / "docs" / (name + "_project_plan.md")
out.parent.mkdir(parents=True, exist_ok=True)
out.write_text("\n".join(lines), encoding="utf-8")
print("\n".join(lines[:12]))
print("... plan ->", out)

运行两个场景对比：

python scripts/domain_project_plan.py it-helpdesk y y 0.2 0.5 --gpu-hours 50
python scripts/domain_project_plan.py legal-assistant n y 20 2 --gpu-hours 300 --high-risk
cat docs/it-helpdesk_project_plan.md

看什么：同一套输入逻辑给出不同路线（帮助台→RAG 优先；法律助手→DAPT+SFT+合规门）；把生成结果交给业务方确认“画像参数”是否真实。

Step 2 填项目章程并定成功指标（10 分钟）

按 docs/{项目}_project_plan.md 补全：

字段 内容
业务目标 一句话（如：工单首响时间降低 30%）
能力清单 问答/格式/多轮/拒答……
成功指标 领域通过率/通用回退/时延/成本
数据来源与合规 哪些系统、脱敏谁负责
干系人 业务方/领域专家/AI 团队
Go/No-Go 标准 PoC 第 4 周评审用

成功指标必须业务方可签字——避免“技术说成功、业务不认账”。

Step 3 PoC 执行与评审（按第 41 章流水线）

  1. 按计划书第 3 节跑 4 周 PoC，资产全部走 manifest；
  2. 第 4 周评审会输出 Go/No-Go：Go 则进入正式化（扩数据→正式训练→上线），No-Go 则记录原因（数据不足/成本超/效果不达）；
  3. 归档：
cd llm-demo
git add docs scripts
git commit -m "project: it-helpdesk plan (RAG route) + legal plan (DAPT+compliance)"
git tag project-plan-v1

立项文档与 PoC 报告是项目最重要的资产之一：它们让“为什么这么做”可追溯，后续迭代（第 44 章）都基于这份基线。

06 参数详解：立项配置速查

参数 参考 说明
PoC 周期 2–4 周 验证最关键假设
种子数据 100–500 条 覆盖能力清单
领域文档触发量 >5GB 考虑 DAPT 视质量而定
成功指标 领域≥80%、通用不掉 业务方签字
预算风险金 +20%–30% 数据返工/重训
高风险任务 人工抽检 100% 医疗/法律/金融

07 高频踩坑排查

坑 1：需求一句话就立项 症状：“做个智能客服”没有能力清单，验收全靠吵。 解法：拆能力清单+每条配验收标准。

坑 2：路线拍脑袋 症状：知识每周更新却选了微调，改一次训一次。 解法：用决策表/生成器按画像定路线。

坑 3：跳过数据摸底 症状：立项时以为有 10 万条，实际只有 200 条干净的。 解法：立项前先跑数据盘点（量/质/合规/可获取性）。

坑 4：无成功指标 症状：上线后不知道算不算成功。 解法：指标写进章程并让业务方签字。

坑 5：忽视合规 症状：用未授权/含 PII 数据训练。 解法：立项书含合规清单（第 08 章）；高风险任务全人工抽检。

坑 6：范围蔓延 症状：做着做着从问答变成“全公司 AI 平台”。 解法：PoC 范围写死；新需求进 v2 列表。

坑 7：时间表是幻想 症状：2 周完成“数据+训练+上线”，实际数据就要 3 周。 解法：按第 41 章流水线与预算反推排期，留风险金。

08 进阶优化：领域落地的进化方向

① 领域平台化：把“数据接入→训练→评测→发布”做成自助平台，新领域只填画像即可启动（第 41 章流水线产品化）。

② 多领域复用：共享底座+多 adapter/多知识库，一个平台服务多个业务线（第 14/43 章）。

③ 评测驱动立项：立项前先建 50 题“业务验收题”，用现成大模型跑基线——数据不足/期望过高在立项时就暴露。

④ 成本治理：按“请求价值”路由大小模型、低峰缩容，把领域模型的单位成本做成可优化的指标。

⑤ 领域专家进流程：专家参与数据评审与 PoC 验收，写进项目章程——领域模型没有领域专家就是盲人摸象。

09 本章核心总结（TOP3）

TOP1：立项先拆“能力清单+验收标准”；路线由四问决定（知识变不变/格式要不要/数据有多少/预算多少），用决策表而不是偏好。

TOP2：PoC 2–4 周验证最关键假设：基线→种子数据→路线 A/B→Go/No-Go；成功指标让业务方签字，预算留 20%–30% 风险金。

TOP3：合规与数据摸底在立项阶段就要做（来源/脱敏/抽检）；项目文档与 PoC 报告是后续迭代的基线资产。
