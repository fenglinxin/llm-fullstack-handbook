01 开篇导语

第 35–36 章的编译收益有个前提：shape 别老变。但真实线上流量恰恰相反——请求长度从 10 到 4000 token 都有，batch 也在动态进出。

编译器的尴尬在于：

  • 固定 shape 编译最优化，但每次新 shape 都可能触发重编译；
  • 全部动态执行，又回到“每算子一次启动”的低效。

工业解法是“分桶”：把连续的长度映射到少数几个“桶”，桶内 padding 到同一长度，每个桶编译/捕获一份——用少量 padding 浪费换掉编译爆炸。

显存侧还有另一组问题：中间 buffer 的分配释放、碎片、CUDA Graph 的固定内存池。本章把“动态 shape + 显存”一起讲，因为它们高度耦合。

一句话记住本章：动态 shape 的工程本质是“在 padding 浪费与重编译开销之间找平衡”，显存侧则要“规划、复用、防碎片”。

02 白话原理：为什么 shape 变会让编译吃亏

2.1 编译器的“形状锁定”

编译器为某个 shape 生成最优 kernel 后，会记住这个 shape。来了新 shape：

  • 若允许动态：可能走通用慢路径或重新编译；
  • 若静态锁定：直接复用最快路径。

CUDA Graph 更严格：它捕获的是一段“固定内存地址+固定形状”的执行序列——地址或形状一变，捕获结果就不能用。

2.2 分桶（Bucketing）思路

真实长度: 37, 128, 95, 4000, 210, 88 ...
桶划分: [1,128], [129,512], [513,2048], [2049,8192]
每个请求 pad 到所在桶上限，执行对应桶的编译产物

代价：短请求被 pad 到 128 时浪费计算；收益：每个桶只编译一次、可捕获 CUDA Graph。

记忆锚点：分桶 = 用“桶内 padding 浪费”买“编译产物复用”；桶边界要按真实长度分布设计，而不是拍脑袋 2 的幂。

03 分桶设计与显存编译器

3.1 分桶设计三原则

  1. 按真实分布切：用线上长度 P50/P90/P99 设计边界，而不是 2 的幂硬切；
  2. 桶数量少而精：4–16 个桶常见；桶越多 padding 越少但编译/显存越多；
  3. 单独处理长尾：>P99 的超长请求走“动态慢路径”，不为它建大桶拖累全体。

3.2 CUDA Graph 桶池

每个桶维护一个 Graph 实例池：

  • 捕获时分配固定内存（graph memory pool）；
  • 请求进入桶→从池里取 Graph 重放；
  • 请求离开→归还池，地址复用。

注意：Graph 捕获期间所有输入张量地址必须稳定；动态 batch 需要“预留最大 batch 的 buffer，用 mask 屏蔽空位”。

3.3 显存编译器在优化什么

优化 做法
内存规划 编译期决定每个中间张量的生命周期，复用 buffer
缓存分配器 PyTorch caching allocator/框架 arena，减少 cudaMalloc
碎片治理 PagedAttention 分块；长请求预分配策略
Graph 内存池 CUDA Graph 专用池，捕获后不再动态分配
激活压缩 checkpointing/融合减少峰值

工程现实：vLLM/SGLang/TRT-LLM 已内置动态批处理与显存池——自研引擎才需要从零做分桶；但理解这些机制能帮你选对框架参数。

05 分步实操：长度分布→分桶→基准实验（约 40 分钟）

Step 1 分桶规划器（10 分钟）

保存 scripts/bucket_planner.py：

# scripts/bucket_planner.py —— 按长度分布生成分桶方案
# 用法：python bucket_planner.py <桶数> [样本数]
import json
import math
import pathlib
import random
import sys

n_buckets = int(sys.argv[1]) if len(sys.argv) > 1 else 6
n = int(sys.argv[2]) if len(sys.argv) > 2 else 20000
root = pathlib.Path(__file__).resolve().parent.parent

random.seed(7)
# 模拟线上长度分布：中位约 400 token，长尾到 8K
lengths = sorted(int(min(8192, max(16, random.lognormvariate(math.log(400), 0.9)))) for _ in range(n))

def pct(p):
    return lengths[min(len(lengths) - 1, int(len(lengths) * p))]

# 计算每桶上限（前一桶上限+1 到当前上限）
upper = []
prev = 0
for b in [pct(k / n_buckets) for k in range(1, n_buckets + 1)]:
    upper.append(max(prev + 1, b))
    prev = b

total_len = sum(lengths)
pad_total = 0
bucket_info = []
for i, lim in enumerate(upper):
    low = 1 if i == 0 else upper[i - 1] + 1
    items = [x for x in lengths if low <= x <= lim]
    if not items:
        continue
    pad = sum(lim - x for x in items)
    pad_total += pad
    bucket_info.append({"bucket": i + 1, "range": [low, lim], "count": len(items),
                        "pad_tokens": pad, "pad_ratio": round(pad / max(1, sum(items)), 4)})

report = {"n_buckets": len(bucket_info), "samples": n,
          "length_p50": pct(0.5), "length_p90": pct(0.9), "length_p99": pct(0.99),
          "total_pad_ratio": round(pad_total / total_len, 4), "buckets": bucket_info}
out = root / "logs" / "bucket_plan.json"
with open(out, "w", encoding="utf-8") as f:
    json.dump(report, f, ensure_ascii=False, indent=2)
print(json.dumps(report, ensure_ascii=False, indent=2))

运行：

python scripts/bucket_planner.py 6
cat logs/bucket_plan.json

看什么：桶边界是否贴合分布（P50/P90/P99）；total_pad_ratio 是否可接受（<10% 通常不错）；长尾是否被单独处理。

生产用法：把线上请求日志的真实长度喂给脚本（替换模拟分布），得到你的专属分桶方案。

Step 2 动态 vs 分桶基准（10 分钟）

保存 scripts/shape_bench.py：

# scripts/shape_bench.py —— 动态编译 vs 分桶静态编译（近似对比）
import json
import pathlib
import time

import torch

device = "cuda" if torch.cuda.is_available() else "cpu"
root = pathlib.Path(__file__).resolve().parent.parent
lengths = [64, 96, 128, 200, 256, 400, 512, 900]

w = torch.randn(256, 256, device=device) * 0.1

def op(x):
    return torch.relu(x @ w)

def sync():
    if device == "cuda":
        torch.cuda.synchronize()

def time_call(fn):
    sync()
    t0 = time.time()
    fn()
    sync()
    return time.time() - t0

# 路径 A：动态编译（每个新长度都可能触发编译/guard 检查）
dyn = torch.compile(op)
t_dyn = sum(time_call(lambda n=n: dyn(torch.randn(n, 256, device=device))) for n in lengths)

# 路径 B：分桶静态编译（桶上限 128/256/512/1024，各编译一次后复用）
bucket_limits = [128, 256, 512, 1024]
def pick_bucket(n):
    for lim in bucket_limits:
        if n <= lim:
            return lim
    return 1024

compiled = {}
def bucket_call(n):
    lim = pick_bucket(n)
    if lim not in compiled:
        compiled[lim] = torch.compile(op)
    x = torch.randn(lim, 256, device=device)
    return compiled[lim](x)

t_bucket = sum(time_call(lambda n=n: bucket_call(n)) for n in lengths)

report = {"device": device, "lengths": lengths,
          "dynamic_total_s": round(t_dyn, 4), "bucket_total_s": round(t_bucket, 4),
          "note": "含首次编译开销；稳态收益需重复调用后测量"}
with open(root / "logs" / "shape_bench.json", "w", encoding="utf-8") as f:
    json.dump(report, f, ensure_ascii=False, indent=2)
print(json.dumps(report, ensure_ascii=False, indent=2))

运行：

python scripts/shape_bench.py
cat logs/shape_bench.json

看什么：首次全量调用下分桶通常更快（编译次数少）；如果差距小，说明你的模型/框架已内置动态处理（vLLM 场景无需自研分桶）。

  2. 自研引擎场景：按 bucket_plan.json 实现分桶调度 + CUDA Graph 桶池 + mask 处理空位；
  3. 监控“padding 浪费率”（pad token/有效 token）与“Graph 命中率”，上线后按真实分布调桶；
  4. 归档：

分桶是“显存/编译开销 ↔ padding 浪费”的权衡：上线后用真实日志每月重算一次桶边界。

06 参数详解：动态 shape 配置速查

参数 参考 说明
桶数 4–16 按分布 P50/P90/P99 切
pad 浪费率 <10% 过高=桶太粗
长尾处理 >P99 走动态路径 不为长尾建大桶
Graph 池大小 每桶 2–8 实例 按并发
dynamic 开关 框架默认 自研编译按需

07 高频踩坑排查

坑 1：桶按 2 的幂硬切 症状：512 的桶装了 90% 的 100-token 请求，浪费巨大。 解法：按真实分布分位切；用本章 planner。

坑 2：桶太多 症状：编译/显存爆炸，收益被吃掉。 解法：4–16 桶起步；差异小的边界合并。

坑 3：CUDA Graph 捕获地址变化 症状：重放报错或结果错。 解法：固定输入 buffer；动态 batch 用“最大容量+mask”。

坑 4：动态重编译爆炸 症状：自研编译下每个新长度都编译。 解法：分桶静态编译；框架场景交给框架。

坑 5：只看编译时间不看稳态 症状：首次调用慢就否定编译。 解法：重复调用测稳态；生产做预热。

坑 6：显存碎片 症状：长时间运行后可用显存越来越少。 解法：用框架缓存分配器/arena；Graph 专用池；监控碎片率。

坑 7：自研重复造轮子 症状：vLLM 已内置动态批处理，还自研分桶。 解法：先确认框架能力；自研只覆盖框架覆盖不了的部分。

08 进阶优化：动态 shape 与显存的进化方向

① vLLM 式动态内核：attention/prefill 内核直接接受运行时长度（mask/分块），无需分桶——框架层的最优解。

② PD 分离后的 shape：prefill 长度分布宽、decode 恒为 1 token/步，分开后各自 shape 特征简单，编译更高效（第 39 章）。

③ TRT profile 多档：TensorRT-LLM 的 min/opt/max profile 本质就是分桶思想，把 opt 对准 P50/P90。

④ 显存池与 VMEM：为长请求预留连续显存段、短请求走池化分配；新硬件显存管理特性持续演进。

⑤ 分布驱动的自适应：根据线上长度分布自动调整桶边界与 Graph 池大小，做成“自调优引擎”。

09 本章核心总结（TOP3）

TOP1：动态 shape 的解法是分桶：按真实分布（P50/P90/P99）切 4–16 桶，桶内 padding、桶间复用编译产物/CUDA Graph，用 <10% 浪费换稳定性能。

TOP2：显存编译器管“规划/复用/碎片”：缓存分配器、Graph 专用池、分页 KV；CUDA Graph 捕获必须固定地址与 shape，动态 batch 用最大容量+mask。

TOP3：vLLM 等框架已内置动态批处理——先用框架参数，自研分桶只用于框架覆盖不到的自研引擎；上线后按月用真实分布重算桶边界。
